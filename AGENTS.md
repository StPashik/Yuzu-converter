# Yuzu Converter

Communicate with the owner in Russian. Use English for documentation, code comments, technical diagnostics, and GitHub releases. The app defaults to English and offers English, Russian, German, French, and Spanish UI; localized resource values are intentionally in those languages. Build the native macOS 13+ app from scratch. Do not alter or import old checkouts, source code, Git history, or caches. The owner explicitly permits reusing the Yuzu Mac App application icon (including its PNG for documentation) and menu bar icon, and now authorizes reading its wheel design and applying that appearance to the current implementation. This design reference does not authorize importing unrelated code, settings, conversion engines, or caches. Do not copy proprietary Tangerine resources or binaries. Research reports may be read as references; separate observations, inferences, and unknowns.

Keep docs/Requirements.md and the accepted docs/Architecture.md current. Scope includes conversion and seven Actions, including the owner-requested Compress to ZIP. Exclude File tools. Do not silently reduce requirements to match a backend; record limitations in docs/Conversion-matrix.md.

Version 0.4.1 was Apple Silicon only. The owner reopened Intel support on October 28, 2026; native Intel CI and the signed Sandbox archive passed. Starting with 0.4.2, publish separate arm64 and x64 releases, both requiring native CI. Advance each signed legacy feed only after its validated assets are public. Never offer an arm64 archive to Intel clients or rewrite historical tags/assets.

Follow GitFlow through GitHub pull requests: feature/* from develop into develop; release/<version> from develop into main, then back into develop. Wait for CI and use merge commits. Tag the exact main release-PR merge commit. Do not commit or push directly to main or develop. A legacy appcast publication may use a separate PR after its referenced assets are public. The owner's request authorizes publishing to StPashik/Yuzu-converter. Never force push or rewrite published tags/assets. Read docs/Releasing.md before preparing a release.

Publish normal releases as stable GitHub Latest releases. Use prerelease status only when the owner explicitly requests a beta/RC. Ad-hoc signing and missing notarization are documented artifact limitations, not reasons to silently choose prerelease status.

The app checks at launch and periodically by default; Settings → About can disable automatic checking. Installation always requires the owner’s confirmation in the update offer or Check for Updates. Release work must not install or upgrade either installed app copy, run global npm installation, quit, relaunch, or restart the owner's app unless explicitly requested. Test installs only in isolated temporary homes. Keep signing keys in this project's Keychain account; do not copy Beamly's keys, application code, or installation behavior.

Make releases useful to people: clear English copy, direct downloads, a short quick start, accurate format support, and accessible documentation. Explain why consequential code choices exist in concise comments; do not narrate obvious code.

Run automated checks in separate scratch paths. New manual checks remain deferred; label physical Finder/Sandbox gates as unverified. Never run concurrent Swift builds in the same scratch path. Verify actual test results, licenses, artifact checksums, version consistency, and known limitations before publishing.
